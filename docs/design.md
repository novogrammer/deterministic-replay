# 決定論的リプレイによる画像生成動画の設計

更新日: 2026-10-02

## 目的

正方形の画像を球体群の表面へ投影し、球体が容器へ流れ込む順再生の動画を生成する。最初は画像が揃っていないように見え、最後に球体が落ち着くと、完成時の視点から画像が揃って見える。

計算した動きを繰り返しプレビューし、同じリプレイをMP4として書き出せるようにする。

## 確定事項と設計上の提案

以下は会話で確定した要件。

- Viteによる静的ページとして構成し、GitHub Pagesへ公開する。
- 入力は正方形の画像。
- Rapier3Dで球体をシミュレーションする。
- 球体が容器に流れ込む表現を基本とし、具体的な容器や流れ方は後で決める。
- 動画は順再生。逆再生で組み上げる方式は採用しない。
- 球体群はThree.jsのInstancedMeshで描画する。
- 各インスタンスに最終姿勢をMatrix4として保持する。
- 最終姿勢はシーンごとに開発時にベイクし、あらかじめ静的データとして持たせる。開発中にベイク・再生成できる仕組みを用意する。
- UVはベイクせず、各インスタンスの最終姿勢からTSLで計算する。
- プレビューは何回もループし、MediabunnyでMP4を書き出す。
- canvasと出力動画は同じ正方形の解像度にする。レンダラーのpixel ratioは1とし、プレビューの表示サイズはCSSで調整する。
- プレビューと動画出力は、時刻評価から描画まで同じ仕組みを使う。
- TypeScriptはクラスベースを基本とする。関数も用途に応じて使う。
- 表示カメラは固定を基本案とする。冒頭に上方を向く演出も候補。

以下の記録方式、データ構造、終了条件、検証方法は、これらを実現するための設計案。数値や具体的なAPI選択は実装時に確認する。

## 見え方を成立させる仕組み

開発時に、球体が落ちて容器に集まる物理シミュレーションを最後まで計算する。その結果をシーンごとの最終姿勢としてベイクし、静的データに保存する。公開ページはそのデータを読み込んで使用する。

描画時には球体のローカル表面座標を最終姿勢で変換し、完成時カメラから投影して入力画像のUVを求める。同じ表面座標を現在姿勢で描画することで、動いている球体にも画像の断片が付いて見える。最後に現在姿勢と最終姿勢が一致すると、断片が完成時の視点でつながる。

最終姿勢は物理計算の結果であり、球体をそこへ強制移動させるための目標姿勢ではない。事前に計算した記録を先頭から順再生する。

球体間の隙間、容器による遮蔽、球体の陰影は残る。完成画像の読みやすさは、容器の形、球体の大きさと密度、カメラ、背景、マテリアルを調整して作る。初期配置では断片が十分に散らばって見えることも確認する。

## 技術構成

| 技術 | 役割 |
| --- | --- |
| Vite | 開発と静的ビルド |
| Three.js / InstancedMesh | 球体群、容器、カメラの描画 |
| TSL | 最終姿勢からの投影UV計算と画像サンプリング |
| Rapier3D | 球体と容器の衝突、固定ステップの物理計算 |
| Mediabunny | 描画したフレームのエンコードとMP4生成 |
| GitHub Pages | ビルド成果物の静的配信 |

処理はブラウザ内で完結させる。画像はユーザーがローカルファイルとして選択し、動画はローカルへダウンロードする設計とする。

TSLを使用するレンダラーはWebGPURendererを第一候補とする。対応するブラウザとバックエンド、インスタンスデータの渡し方は、採用バージョンで検証して決める。

## HTML・SCSS・JavaScriptの実装方針

- SCSSのUIクラス命名はBEMを使う。ブロックは`block`、要素は`block__element`、状態やバリエーションは`block--modifier`とする。リセット用には`body`などの要素セレクタを使う。
- UIと描画用canvasを含め、HTMLノードは`src/index.html`に記述する。JavaScriptでノードを生成・追加しない。
- JavaScriptは既存ノードの参照、イベント登録、表示状態や値の更新を担当する。HTML文字列による構造の生成・置換も行わない。
- Three.jsのレンダラーにはHTMLに記述したcanvasを渡す。プレビュー、書き出し、開発用ベイクで必要なHTMLノードもこの方針に従う。

## TypeScriptの実装方針

状態とリソースの所有者を明確にするため、クラスベースを基本とする。シーン、レンダラー、リプレイ、再生制御、動画出力など、状態やライフサイクルを持つ責務をクラスで管理する。

クラスを使うためだけのラッパーや継承階層は作らない。補間、データ変換、設定の検証など、独立した計算は関数として実装できる。TSLのノード構築にも必要に応じて関数を使う。

## プレビューと動画出力の共通描画

時刻を秒で指定する`renderAt(timeSeconds)`を共通の描画入口とする案。指定時刻の球体姿勢、出現状態、表示カメラ、完成状態の保持を評価し、同じシーン・マテリアル・レンダラー・canvasで描画する。呼び出し側によって見た目の計算を分岐させない。

| クラス案 | 責務 |
| --- | --- |
| ScenePlayer | リプレイと描画リソースを持ち、`renderAt`で時刻評価から描画まで実行する |
| PreviewController | 再生時刻、一時停止、ループを管理し、ScenePlayerの`renderAt`を呼ぶ |
| VideoExporter | 出力フレームの時刻を決め、同じScenePlayerの`renderAt`後にMediabunnyへフレームを渡す |

クラス名と具体的な分割は設計案。共通化する対象は描画呼び出しだけでなく、その前の姿勢補間、カメラ更新、投影UVの設定も含む。描画処理の内部で実時間の差分を積算せず、指定した時刻から描画状態を求める。

プレビューは再生時計から求めた時刻を渡す。動画出力はフレームnに対してn / FPSを渡し、描画完了とフレーム追加を待って次へ進む。同じ時刻なら、どちらの呼び出しでも同じ描画状態になる。

書き出し中はプレビューの時計更新を一時停止し、動画出力が同じcanvasを使う。完了・キャンセル・失敗時には、保存していたプレビュー時刻を共通処理で再描画し、元の再生／一時停止状態へ戻す。

## canvasの描画解像度と表示サイズ

canvasの描画バッファと動画は、同じN × Nピクセルの正方形とする。Nの具体値は未決定。プレビューも動画と同じ解像度で描画し、画面に収まるようCSSで縮小表示する。

```ts
renderer.setPixelRatio(1)
renderer.setSize(outputSize, outputSize, false)
```

端末の`window.devicePixelRatio`自体は変更せず、レンダラーのpixel ratioに1を指定する。`setSize`の第3引数をfalseにしてcanvasのインライン表示サイズを更新せず、SCSSで表示幅と縦横比を管理する。[Three.js: Renderer](https://threejs.org/docs/pages/Renderer.html#setSize)

表示幅は利用可能な幅と出力サイズの小さい方を基準にし、必要に応じて画面の高さにも収まるようにする。画面のリサイズではCSSの表示サイズだけを変え、描画バッファ、動画の解像度、カメラの縦横比は変えない。透視投影カメラのaspectは1とし、平行投影の場合も正方形の投影範囲を保つ。出力解像度を明示的に変更する際に描画バッファを更新する。

MediabunnyにはCSSで縮小された表示ではなく、元のcanvasのN × Nピクセルを渡す。CSSで小さく表示しても描画の計算量はN × Nのままなので、Nはプレビュー性能も含めて決める。

## 開発時のシーンベイク

ここでベイクするのは物理シミュレーションの結果、特に各インスタンスの最終姿勢。UVや入力画像の色はベイクしない。

1. シーンID、シーン設定、固定シードから、球体、容器、初期条件を生成する。
2. 固定タイムステップで物理計算を進め、終了条件まで計算する。
3. 各球体のID、最終姿勢のMatrix4、終了ステップ、再現に必要な設定とバージョン情報を保存する。
4. 完成時カメラと画像領域をシーンの設定に対応付ける。
5. ベイク結果を読み込み、完成状態と順再生の見え方を確認する。
6. 確認済みのデータを静的アセットとしてビルドに含める。

開発用のベイク操作は、ローカルの開発画面、またはローカルスクリプトとして用意する。計算開始、進捗表示、結果の保存、再読み込みができるようにする。具体的な操作方法とファイル形式は未決定。

最終姿勢は入力画像に依存しない。同じシーンに別の画像を読み込んでも再ベイクしない。容器、球体数・半径、初期条件、投入順、物理設定、タイムステップ、終了条件、Rapierバージョンなど、物理結果に影響する設定を変更した場合は再ベイクする。カメラや画像領域だけの変更では、保存した最終姿勢を再利用して投影設定を更新できる。

シーン設定の識別情報をベイク結果に含め、古い設定の最終姿勢を新しいシーンへ適用しないようにする。

## 公開ページの処理の流れ

1. 選択したシーンの設定とベイク済み最終姿勢を読み込む。
2. 正方形の画像を読み込み、画像テクスチャを準備する。
3. そのシーンのリプレイデータを準備する。
4. リプレイ時刻から現在姿勢を取り出し、TSLでベイク済み最終姿勢からUVを計算してループプレビューする。
5. 書き出し時は同じリプレイと描画処理を使い、指定FPSの時刻でフレームを生成してMP4へ保存する。

最終姿勢は公開ページで毎回求め直さない。動きの供給方法は、ベイク時に時系列の姿勢記録も保存して配信する案と、ベイク時と同じ条件でブラウザ内のRapierを順再生し、記録を生成する案がある。両者の配信サイズと準備時間を比較して決める。後者では終端がベイク済み最終姿勢と一致することを検証し、位置合わせのための強制移動で補正しない。

ブラウザ内で記録を生成する場合は、生成中に進捗を表示する。配信済みの記録を使う場合は、読み込み後にプレビューを開始できる。

## 姿勢と投影UV

インスタンスIDと球体IDは、記録、描画、最終姿勢データを通して固定する。

| データ | 内容 | 更新タイミング |
| --- | --- | --- |
| 現在姿勢 | リプレイ時刻の位置と回転 | 各描画フレーム |
| 最終姿勢 | 開発時にベイクした終了時のMatrix4 | シーンの読み込み時。開発時は再ベイクで更新 |
| 投影用カメラ | 完成時のView・Projection行列 | 完成構図の設定時 |
| 表示用カメラ | その時刻に画面を描画するカメラ | 固定、または時刻に応じて更新 |
| 画像領域 | 投影画面内の正方形領域 | 完成構図の設定時 |

最終姿勢はMatrix4で保存・使用する。位置・回転・スケールを一つの変換として扱い、TSLでローカル表面座標に行列を適用する。GPUへもこの行列を渡す。具体的なインスタンス属性／バッファ形式とファイルのシリアライズ形式は実装時に選択する。

Float32で保持する場合、行列本体は各インスタンス16成分／64バイト。GPUバッファのアラインメントや追加属性、ファイル形式によるサイズの増加は別途考慮する。

リプレイ中の現在姿勢は補間するため、位置＋Quaternionで記録する案を維持する。最終姿勢は固定値なので、同じ形式に揃える必要はない。球体でも投影模様はローカル表面に対応するため、最終回転を省略しない。

投影計算の概念式は以下。実装APIを示すコードではない。

```text
pLocal      = 球体表面のローカル座標
pFinalWorld = meshWorldMatrix × finalInstanceMatrix[id] × vec4(pLocal, 1)
pClip       = finalProjectionMatrix × finalViewMatrix × pFinalWorld
pNdc        = pClip.xy / pClip.w
uvScreen    = pNdc × 0.5 + 0.5
uvImage     = (uvScreen - imageRegionMin) / imageRegionSize
surfaceColor = sample(inputImage, uvImage)
```

ここでは最終インスタンス行列をメッシュのローカル座標系で保持する。ワールド姿勢を保持する場合は、meshWorldMatrixを重ねて適用しない。現在姿勢と最終姿勢の座標系を統一する。

描画位置は別に、現在インスタンス行列と表示用カメラで求める。UV計算に現在姿勢や表示用カメラの動きを混ぜない。

投影に使うのは球体の中心ではなく、球体表面の座標。表面上の位置ごとに画像をサンプリングし、球体全体を一色にする方式にはしない。UV属性やUVテクスチャとして計算結果を保存する方式も採用しない。

実装ではローカル表面座標をフラグメントへ渡し、TSLで最終姿勢による投影と透視除算を行う構成を候補とする。頂点で計算したUVをそのまま補間する場合は、別視点での投影の歪みを検証する。

画像の上下方向、テクスチャの色空間、投影範囲外やカメラ背後の表面の扱いを明示する。範囲外は背景色などで処理し、画像端の意図しない引き延ばしを避ける。正方形の出力画面内で、画像領域も正方形として定義する。

## 決定論と記録

二つの再現性を分けて扱う。

- 記録の再現性: 同じ記録と同じ時刻から、同じ位置・回転・カメラ状態を取り出せる。
- 再計算の再現性: 同じ初期条件、生成順、物理設定、Rapierバージョンから、同じ計算結果を得られる。

Rapierの公式資料では、同じバージョンと初期条件でのクロスプラットフォーム決定論を説明している。ただし初期値の計算も決定的である必要がある。固定シードだけで十分とはせず、乱数の実装、球体の生成順、追加・削除のステップ、設定値を固定する。初期条件を作るMath.sin / Math.cosなどの超越関数には、環境差が生じうる点も考慮する。[Rapier: Determinism](https://rapier.rs/docs/user_guides/javascript/determinism/)

物理計算へrequestAnimationFrameの経過時間を直接渡さない。生成タイミングや終了判定も整数のステップ番号に基づける。依存バージョンとロックファイルを固定し、記録に生成設定とバージョン情報を対応付ける。

GPU描画のピクセル値やMP4のバイト列が、異なる端末で完全一致することまでは要件にしない。

### 記録データ案

- メタデータ: シーンID、データ形式バージョン、シーン設定の識別情報、固定シード、物理設定、球体数、タイムステップ、ステップ数、依存バージョン。
- 静的データ: 球体ID、半径、最終姿勢のMatrix4、投影用カメラ、画像領域。
- 時系列データ: 各ステップの位置3成分、クォータニオン4成分。
- 演出データ: 出現ステップ、表示カメラの動き、完成状態の保持時間。

最終姿勢の静的データはシーンごとに必ず保存する。時系列データまで静的配信するかどうかは未決定。どちらの場合も、同じシーンIDと設定に対応するデータを使う。

初期状態をステップ0として保存し、各物理ステップの終了状態を続けて記録する。途中で球体を生成する場合は、出現前のインスタンスを描画しない。

Float32で位置・回転の7成分を保存する場合、姿勢記録の目安は「球体数 × サンプル数 × 7 × 4バイト」。球体数や尺を決める際は、この記録、GPUデータ、画像、動画出力バッファの合計メモリを確認する。

### 終了条件

終了条件は未確定。全球体の投入後、速度などが閾値以下になった状態を一定ステップ確認する方法を候補とする。最大ステップ数も設定し、未収束の場合はその状態を示す。

ベイク済み最終姿勢は記録の最終サンプルと一致させる。ブラウザ内で再計算する方式でも、ベイク時に保存した終了ステップで比較する。終盤の保持区間ではその姿勢を使い、物理計算を追加して完成画像がずれないようにする。

## ループプレビューとカメラ

物理Worldをループのたびに再計算せず、記録の時刻だけを先頭へ戻す。

再生時刻に対応するサンプルを取り出し、必要に応じて位置を線形補間、回転をクォータニオン補間する。この時刻評価処理をプレビューと書き出しで共有する。

1周期は「落下・収束」と「完成状態の保持」を合わせたものとする案。保持後に先頭へ戻るカットを許容し、継ぎ目のない物理ループは初期要件に含めない。

カメラは固定を基本案とする。上から落ちる様子を見せたい場合は、冒頭に上を向き、終盤に完成構図へ移る。表示カメラの動きはリプレイ時刻の関数として定義し、投影用カメラは完成時の設定に固定する。

## MP4書き出し

MediabunnyのOutput、Mp4OutputFormat、CanvasSourceを利用する構成を候補とする。CanvasSourceは明示的な時刻でcanvasのフレームを追加できる。フレーム追加のPromiseを待ち、バックプレッシャーに従って処理する。[Media sources](https://mediabunny.dev/guide/media-sources)、[Writing media files](https://mediabunny.dev/guide/writing-media-files)

出力FPSをFとすると、フレームnの評価時刻はn / F、フレームの長さは1 / Fとする。実時間の録画速度に依存させず、各時刻の姿勢とカメラを評価し、描画の完了を確認してからフレームを追加する。

初期案ではプレビューの1周期を1本の動画として出力する。完成状態の保持区間を末尾に含め、先頭へ戻るカットは動画内に挿入しない。出力フレーム数と周期の長さを合わせ、最終姿勢を表示するフレームが含まれることを確認する。

AVC / H.264を第一候補とし、実行環境で指定解像度と設定のエンコード可否を確認する。使用不可の場合は書き出せない理由を表示する。書き出し中は入力画像や設定を固定し、プレビューの時刻更新が出力フレームを上書きしない構成にする。

解像度、FPS、画質、キャンセル方法は未決定。メモリ上にMP4を保持する方式から始めるか、大きな出力のために別の保存方式を採用するかは、動画サイズを測って決める。

## 静的公開

GitHub Pagesのリポジトリ配下に公開する場合は、Viteのbaseを公開パスに合わせる。ユーザーサイトやカスタムドメインの場合は設定が異なる。画像以外の静的アセットやRapierのWASMも、公開パスから読み込めるようにする。[Vite: Deploying a Static Site](https://vite.dev/guide/static-deploy.html)

公開対象リポジトリ、公開URL、ビルド／配信手順は未決定。このdocs作成では、外部サービスの変更、デプロイ、pushは行わない。

## 未決定事項

- 容器の形: 単純な容器、漏斗、砂時計など。
- 球体数、半径、投入位置、投入間隔、物理パラメータ。
- 完成画像が見やすい容器の密度とカメラの投影方式。
- 固定カメラか、上方から完成構図へ移るカメラか。
- 背景、照明、球体と容器のマテリアル。
- 固定タイムステップ、終了閾値、最大計算時間、動画尺、保持時間。
- 出力解像度、FPS、画質、対応ブラウザ。
- 正方形でない画像を拒否するか、クロップするか。
- UIで変更できる設定の範囲と、物理計算のWorker化。
- 開発用ベイクの操作方法、保存形式、シーン設定との整合性確認方法。
- 時系列の姿勢記録も静的配信するか、公開ページで決定論的に再計算して記録を生成するか。

## 実装時の確認項目

- 最終姿勢で静止表示すると、指定視点から入力画像が揃って見える。
- 球体が回転・移動しても、表面の模様は最終姿勢から求めた投影に対応する。
- UVの上下、座標系、画像領域が正しく、表示カメラの移動で投影UVが変わらない。
- 固定条件で再計算した姿勢記録が一致する。検証範囲は使用バージョンと環境を明記する。
- シーンのベイク結果を保存・再読み込みでき、球体IDと最終姿勢の対応が保たれる。
- 入力画像の差し替えで再ベイクが不要であり、物理設定の変更時には古いベイク結果を検出できる。
- 順再生の終端とベイク済み最終姿勢が一致し、強制移動による補正を必要としない。
- ループを繰り返しても記録と最終姿勢が変化しない。
- プレビューと書き出しで、同じ時刻の球体姿勢とカメラ状態が一致する。
- プレビューと書き出しが同じ時刻評価・描画処理を使い、書き出し終了時に元のプレビュー状態へ戻る。
- MP4が再生でき、想定した尺、FPS、解像度、完成状態の保持区間を持つ。
- DPRの異なる端末や画面リサイズでもcanvasの描画バッファが指定のN × Nを保ち、動画の解像度と一致する。
- GitHub Pagesの公開パスで、アセットとWASMが読み込める。
- 計算、プレビュー、書き出しのメモリ使用量が想定した端末で許容範囲に収まる。
